# Постоянные контексты и hot reload логики

Реализация: `C:\src\DasForUE2`, Unreal Engine 5.8.3, Win64 Development.

## Поведение

`ADasProbeActor::ExecuteDas` теперь использует `FDasRuntimeModule::RunPersistent`.
Каждая пара «объект + путь скрипта» получает свой Program/Context. Повторные вызовы
используют уже скомпилированную функцию и сохраняют глобальные переменные VM.
Разные Actor, а также editor/PIE worlds, не разделяют состояние.

Перед очередным вызовом runtime сравнивает содержимое исходника и файлов,
которые загрузил компилятор, включая импорты. При изменении готовится новый
Program/Context. После успешной инициализации и проверки сигнатуры `main(int):int`
он заменяет прежнюю версию между вызовами. Фоновый watcher пока не используется:
обновление произойдёт при следующем вызове скрипта.

Ошибки компиляции, сигнатуры или инициализации оставляют старую версию активной.
`FDasExecutionResult.ReloadError` содержит диагностику отклонённого обновления;
`Revision` — номер принятой версии. В Output Log выводится сообщение
`Reload rejected`. Неизменённый ошибочный исходник повторно не компилируется.

Инициализатор кандидата не получает `self`, поэтому не может изменить свойства
действующего Actor через наши native API. После принятия скрипта ошибки выполнения
возвращаются через `Error`; следующий вызов очищает состояние исключения.
Откат уже выполненных действий или автоматический откат кода после runtime panic
в этот этап не входят.

## Состояние между версиями

Для переноса состояния реализован первый явный контракт: именованные `int32`.
Он не определяет будущий синтаксис DSL.

```das
options gen2
require ue_foundation

[export]
def main(input:int):int {
    let count = ue_state_get_int("count", 0) + input
    ue_state_set_int("count", count)
    return count
}
```

Готовый пример:
`C:\src\DasForUE2\Plugins\DasForUE\Content\Das\Scripts\persistent_counter.das`.

У первого Actor два вызова с аргументом `1` вернут `1`, затем `2`; у второго первый
вызов вернёт `1`. После изменения последней строки на `return count + 100`
следующие вызовы вернут соответственно `103` и `102`. При ошибке синтаксиса
продолжит работать предыдущая версия с теми же счётчиками.

Обычные глобальные переменные сохраняются между вызовами одного контекста, но
переинициализируются при смене версии. Произвольная память VM, строки, контейнеры
и указатели не копируются. Для таких типов потребуется отдельная схема миграции.
Значения UPROPERTY остаются в существующем объекте при обновлении только логики.

## Владение и очистка

Контекст хранит слабую ссылку на владельца. `EndPlay` и `Destroyed` освобождают
контексты Actor, очистка World удаляет оставшиеся контексты этого мира,
post-GC удаляет контексты умерших UObject. При shutdown контексты уничтожаются
до остановки daScript. `ReleaseObject` позволяет явно сбросить сессии объекта.
`RunFile` по-прежнему создаёт независимый временный контекст для разового запуска.

## Границы этапа и продолжение

Сейчас компиляция и проверка файлов синхронные, на game thread; каждый объект
компилирует свою версию. Это проверяемая основа механизма, ещё не оптимизированный
runtime для большого числа Actor. Следующие улучшения: общий кеш скомпилированных
модулей, очередь файловых изменений и контролируемые точки обновления.

Обновление схемы класса с Blueprint reinstancing пока создаёт новый контекст:
перенос script-state между заменёнными UObject ещё не реализован. Сохранение
UPROPERTY при структурном reload проверяется отдельно существующим тестом.

Lifecycle-вызовы `BeginPlay`, `Tick`, `EndPlay` теперь реализованы; см. Docs/Lifecycle.md.
Следующий функциональный шаг — delegates/подписки с корректным снятием при reload.
Полный DSL классов и расширенная типизированная миграция остаются отдельными
этапами; пользовательский синтаксис DSL ещё не выбран.
