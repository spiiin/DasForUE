# TArray: первый срез

Поддержаны верхнеуровневые параметры TArray<int32>, TArray<float>, TArray<double>,
TArray<bool>, TArray<FString> и TArray<FName>. Генератор использует array<T> daScript,
а для FName — array<UEName>. Работают input/const-ref, return, чистый out и inout.
Текущий выбор: 27 функций. Функции массивов пока представлены тестовым fixture API.

```das
let self = C_DasObjectFixture_5f019a81_from(ue_self_object())
let input <- [1, 2, 3]
let result <- fixture_TransformInts(self, input)
verify(result[0] == 11)
verify(input[0] == 1)

let strings <- ["hello", "Привет"]
let changed <- fixture_MutateStrings(self, strings)
verify(changed.out_copy[2] == "世界")
verify(length(strings) == 2)
```

Массивы и result-структуры с массивами возвращаются через move (`let result <- ...`).
Входы копируются в UE call frame; изменение inout не меняет массив скрипта на месте:
обновлённое значение находится в result. Возвращённые массивы и строки принадлежат
daScript и сохраняются после освобождения call frame. Результат можно передать
в следующий вызов. Полный пример: Content/Das/Scripts/generated_arrays.das в плагине.
generated_arrays_bad_type.das — отрицательный тест, а не рабочий пример.

## Runtime и проверки

ue_arg_array(call, path, size) создаёт или полностью сбрасывает входной массив.
Элементы задаются существующими ue_arg_int/string/name/... по пути values.0,
values.1 и т. д. Каждый элемент необходимо записать после последнего сброса.
Перед ProcessEvent проверяется полнота заполнения всех входных массивов.
Пустой массив нужно явно задать размером 0 — отсутствие аргумента не означает пустоту.

После вызова ue_result_array_size возвращает размер, а ue_result_int/string/name/...
читают элементы по индексированному пути. Проверяются тип, направление параметра,
фаза вызова, целочисленный индекс, переполнение и границы. Освобождённые frames
использовать нельзя. Генератор делает эти операции автоматически.

Лимит — 65 536 элементов на один массив. Отрицательный/слишком большой размер
входа отклоняется до выделения массива и выполнения UFunction. Слишком большой
выход обнаруживается после ProcessEvent, поэтому побочные эффекты функции уже
могли произойти и не откатываются. Это лимит количества элементов, а не общий
лимит памяти всех строк, массивов или call frames.

FStructOnScope владеет памятью UE-параметров и уничтожает массивы/строки при
освобождении frame, включая выход из VM после ошибки. Raw UE-указатели скрипту
не передаются. Объектных элементов в этом срезе нет, дополнительных GC-pins нет.

## IR и границы

IR v3 расширен kind=array. parameters[].element описывает тип элемента;
type_path содержит имя класса FProperty элемента (например, IntProperty).
В fields массив представлен одним узлом, без развёртывания динамических индексов.
Контрольная сигнатура UFunction теперь включает описание array inner property,
поэтому смена типа элемента обнаруживается до вызова сгенерированной обёртки.
Генератор сверяет тип элемента с IR и отклоняет неизвестные варианты.

Массивы enum, UObject и структур, вложенные массивы, массивы внутри value-структур,
фиксированные C++ массивы и default_text для массивов пока отклоняются явно.
Массив UObject требует отдельного GC-aware маршаллинга; поддержка общего
UObject-параметра сама по себе недостаточна. TMap/TSet остаются отдельными этапами.

Дальнейший порядок: массивы структур и UObject с GC, затем TMap/TSet; модель
authoring DSL, макросы с выбранным пользователем синтаксисом, hot reload тел
методов и затем состава классов. AOT и production packaging остаются в плане.
Модель DSL можно сделать следующим приоритетом, если полный набор контейнеров
не нужен для первого пользовательского сценария.
